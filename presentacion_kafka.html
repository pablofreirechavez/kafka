2. ¿Por qué no usar MySQL o PostgreSQL?

Las bases de datos relacionales están diseñadas para almacenar el estado actual, no para procesar flujos masivos de eventos continuos.

  • Cuellos de botella: Escribir 100,000 ubicaciones por segundo bloquea las tablas.
  • Falta de reactividad: Las apps tendrían que consultar la base de datos constantemente ("¿Ya llegó el auto?") en lugar de recibir alertas.

El Patrón Anti-Patrón

UPDATE drivers
SET lat = -2.189, lng = -79.889
WHERE driver_id = 405;
-- Ejecutado millones de veces por minuto

3. Kafka: El Sistema Nervioso Central

En lugar de actualizar una base de datos, las aplicaciones publican un "Evento" (algo que ya ocurrió). Kafka recibe todos estos eventos y los distribuye a quienes les importe.

5. Los Tópicos (Topics)

Un tópico es el canal o la categoría donde se envían los mensajes. Piénsalo como una tabla de base de datos, pero orientada a eventos.

driver-locations

Recibe el GPS de todos los autos cada pocos segundos. Altísimo volumen de datos.

ride-requests

Contiene las solicitudes de los usuarios buscando transporte.

trip-events

Estados del viaje: "Iniciado", "En camino", "Finalizado".

6. Particiones (La clave de la escalabilidad)

Si la ciudad entera envía datos a un solo tópico, el servidor colapsaría. Kafka divide el tópico en Particiones.

  • Permite procesar datos en paralelo.
  • Partition Key: Usamos el ID del conductor. Así garantizamos que todo el recorrido del Auto A vaya en orden por la misma partición.

7. Los Consumidores (Consumers)

Servicios backend que se suscriben a los tópicos y reaccionan en tiempo real. Un mismo mensaje puede ser leído por múltiples servicios sin borrarse.

Evento: Viaje Finalizado en `trip-events`

1. Servicio de Cobro: Lee el evento y hace el cargo a la tarjeta.
2. Servicio de Reputación: Habilita la pantalla para calificar al conductor.
3. Servicio de Notificación: Envía el recibo por correo.

9. Flujo Real: El Matchmaking Engine

El motor de emparejamiento (Consumer) necesita saber dos cosas al mismo tiempo:

  1. Quién pide el viaje (lee ride-requests).
  2. Dónde están los autos (lee driver-locations).

Cruza ambos streams en tiempo real (KStreams), calcula distancias, y emite un nuevo evento al tópico driver-dispatch.

Stream Processing

Procesamiento de datos en pleno vuelo sin tocar una base de datos estática.

10. Flujo Real: Tarifa Dinámica (Surge Pricing)

¿Cómo sabe la app cuándo subir el precio porque está lloviendo o hay un concierto?

  • Un servicio cuenta cuántos mensajes entran a ride-requests (alta demanda).
  • Cuenta cuántos autos con estado "AVAILABLE" hay en driver-locations (baja oferta).
  • Si la demanda supera a la oferta, publica un multiplicador de tarifa en pricing-updates instantáneamente.

12. Tolerancia a Fallos (Replicación)

¿Qué pasa si el servidor de Kafka que guarda tu viaje se quema justo a la mitad del trayecto?

  • Kafka usa el modelo Leader - Follower.
  • Si el Broker líder cae, un servidor seguidor que tiene una copia exacta asume el mando en milisegundos.

Kafka permite que arquitecturas complejas como el Ride-Sharing sean escalables, desacopladas y reaccionen en tiempo real. Es el puente entre los eventos físicos y la lógica digital.
